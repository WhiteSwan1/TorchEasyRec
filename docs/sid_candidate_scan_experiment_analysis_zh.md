### 步骤 3：将排序加二分查找改为可复用哈希索引

提交：`64cf94460253bcddeef9990505bd7d3787b8d7a8`

生产代码只修改了 `tzrec/tools/sid/resolve_sid_collisions.py` 中的 `_ItemIdLookup`：

1. 旧实现先对全部 overflow item ID 执行稳定 `np.argsort`，保存排序后的 ID 和“排序位置到请求位置”的映射。每读取一个源数据 batch，都对 batch 中的所有 ID 调用 `np.searchsorted`，随后再比较字符串以排除不存在的 ID。对于字符串 ID，这会在 4,286 万行扫描中重复执行大量对象字符串比较，复杂度约为 `O(M log M + N log M)`。
1. 新实现只在确实创建 `_ItemIdLookup` 时延迟导入 pandas，不增加 random 策略或无 overflow 路径的启动依赖。
1. 在构造函数中调用 `pd.factorize(item_ids, sort=False)`，一次得到每个请求行对应的 unique 编号和 unique ID。`sort=False` 保留请求 ID 的首次出现顺序。
1. 新增 `_LOOKUP_CHUNK_ROWS = 1_000_000`。按百万行分块使用 `np.minimum.at`，计算每个 unique ID 在 overflow 请求数组中的第一个代表位置，避免额外创建多个全长临时索引数组。该常量只限制临时数组大小，不改变读取 batch 或算法结果。
1. 再按相同大小分块找出所有重复请求行，并记录每个重复行对应的代表行。最终的 `broadcast_duplicate_targets()` 接口保持不变。
1. 使用 unique ID 构建一次持久化 `pd.Index`。`match()` 改为调用 `Index.get_indexer(batch_ids)`，负数表示未命中；命中的 unique 位置再通过 `unique_to_requested` 映射回 overflow 代表行。扫描复杂度变为期望 `O(M + N)` 的哈希工作。
1. 没有改变重复 ID 语义：同一 ID 每次在源数据中出现时，都会写入同一个代表位置；后读取的 batch 继续覆盖先前值，因此仍由源数据中最后一次出现的 candidate 生效；扫描结束后再广播给所有重复 overflow 行。

这一步没有改成按 `overflow_rows` 直接取 candidate。后者依赖两次 Reader 的物理行序，在 ODPS、多文件 glob 或重复 ID 场景下可能改变结果，不能作为通用优化。

对应测试修改位于 `tzrec/tools/sid/resolve_sid_collisions_test.py`：

- 在重复 item ID 的端到端测试中新增最终 `codebook` 精确断言 `[[0, 0], [0, 2], [0, 3]]`，不再只检查输出中是否保留重复 ID。
- 扩展 `_ItemIdLookup` 测试：先为 `b` 写入 `[10, 11]`，模拟其在后续源 batch 再次出现并写入 `[30, 31]`，最后验证所有重复 `b` 都广播为 `[30, 31]`。该测试明确锁定“最后一个源记录生效”的行为。

除提交中的单元测试外，还使用整数和字符串 ID 各做了 500 组随机差分检查；该检查属于实验验证脚本，没有写入生产代码或正式测试文件。新旧查找结果及重复项广播逐项一致。

### 步骤 5：先用微基准判断多核方向

- 这一步没有修改被 Git 跟踪的生产文件。实验直接调用 `pyarrow.parquet.ParquetFile.iter_batches`，只读取前 96 个 row group，共 3,145,728 行。

### 步骤 6：为 SID 工具启用 Arrow 有序线程读取

提交：`d0b8766b4fcb92b261c28288b4729b4dc73aba01`

该提交修改四个被 Git 跟踪的文件：

- `tzrec/datasets/parquet_dataset.py`
  - 为内部 `_reader_iter()` 新增 `use_threads: bool = False` 参数，将原来写死的 `ParquetFile.iter_batches(..., use_threads=False)` 改为传入该参数。
  - 为 `ParquetReader.__init__()` 新增同名参数，默认值仍为 `False`，保存到 `self._use_threads`，并在 `to_batches()` 调用 `_reader_iter()` 时继续传递。
  - 默认值不变，因此训练、评估和其他现有 `ParquetReader` 调用者不会被全局切换到新行为。
- `tzrec/tools/sid/resolve_sid_collisions.py`
  - `CollisionResolutionRunner._make_reader()` 在调用 `create_reader()` 时新增 `use_threads=True`。因此该 SID 工具的 SID 首遍读取和 candidate 第二遍读取都会启用 Arrow 线程读取。
  - CSV 和 ODPS Reader 通过已有的 `**kwargs` 接收但不使用该参数，原有 I/O 语义不变。
- `tzrec/datasets/parquet_dataset_test.py`
  - 新增 `test_use_threads_is_forwarded`，构造开启线程的 `ParquetReader`，mock `_reader_iter` 并断言它收到 `use_threads=True`。
- `tzrec/tools/sid/resolve_sid_collisions_test.py`
  - 扩展现有 Reader projection 测试，断言 SID 工具创建的每个 Reader 都携带 `use_threads=True`，同时继续验证不同策略只读取所需字段。

这一步没有实现 2/4/8 个 Reader 并行，也没有让线程并发写共享 candidate 矩阵。`iter_batches(use_threads=True)` 保持 batch 输出顺序，因此不会破坏重复 ID 的“最后一个源记录生效”语义；实测它只带来有限加速，平均 CPU 仍约为一个核。

## 实验 1：可复用哈希索引

提交：`64cf94460253bcddeef9990505bd7d3787b8d7a8`

被测改动：

- 仅对待处理的 overflow 商品 ID 执行一次因子化。
- 为唯一 ID 构建一个可复用的 pandas 哈希索引。
- 每个源数据批次通过 `Index.get_indexer()` 进行匹配，替代在已排序的字符串 ID 对象数组上重复执行二分查找。
- 保留现有语义：源数据中最后出现的记录提供候选值，该候选值随后被广播至重复的 overflow 行。

预期查找复杂度从约 `O(N log M)` 次字符串比较降低为期望 `O(N + M)` 的哈希操作，其中 `N` 是输入行数，`M` 是 overflow 行数。Parquet 数据和命令与实验 0 相同，因此两次实验的耗时可以直接比较。

实验结果：

| 指标              |       基线 |    哈希索引 |            变化 |
| ----------------- | ---------: | ----------: | --------------: |
| 端到端耗时        |  713.836 s |   464.519 s |         -34.93% |
| 用户态 CPU 时间   |  479.555 s |   344.301 s |         -28.20% |
| 系统态 CPU 时间   |  132.082 s |   120.231 s |          -8.97% |
| 平均 CPU 使用率   |     85.68% |     100.00% | +14.32 个百分点 |
| 候选有效吞吐量    | 72.2K 行/s | 120.7K 行/s |         +67.23% |
| 候选扫描估算耗时  |    593.7 s |     355.0 s |         -40.20% |
| 观测到的 RSS 峰值 |  约 11 GiB | 约 11.1 GiB |      无明显变化 |

完整的碰撞统计完全一致：总商品数 42,864,043，原始碰撞桶数 210,170，重定位商品数 1,403,836，无未解决商品，无最终碰撞桶，最终桶的最大容量为 5。

实测端到端节省 249.317 秒。根据进度检查点估算，候选扫描节省 238.674 秒，占整体运行时间改进的 95.7%。这证明被修改的查找逻辑确实位于实测瓶颈上，汇总统计没有变化。

第一次 A/B 实验并不是完全受控的冷缓存对比。实验 0 在实验 1 之前填充了页面缓存：即使未改动的第一次 SID 扫描，吞吐量也从 3.15M 行/s 提升到 4.90M 行/s，而实验 1 的物理读取字节数几乎没有变化。因此，34.93% 是实际观察到的运行改进，不能视为仅由哈希索引带来的收益。在确认独立优化效果前，需要补充热缓存基线对照实验。

## 实验 0b：热缓存基线对照

在实验 1 之后，再次使用相同输入、命令和页面缓存状态运行未修改的基线提交。在不清理整台主机缓存、也不影响其他工作负载的前提下，该实验控制了已知最大的环境差异。

实验结果：

| 指标             | 热缓存基线 |    哈希索引 |           变化 |
| ---------------- | ---------: | ----------: | -------------: |
| 端到端耗时       |  599.451 s |   464.519 s |        -22.51% |
| CPU 总时间       |  598.698 s |   464.532 s |        -22.41% |
| 平均 CPU 使用率  |     99.87% |     100.00% | +0.13 个百分点 |

| 候选扫描估算耗时 |    479.1 s |     355.0 s |        -25.89% |

热缓存基线产生的完整碰撞统计与前两次运行完全相同。因此，在缓存和 CPU 利用率几乎一致的受控对比下，端到端节省 134.932 秒，吞吐量提升至 1.290 倍；其中约 124.0 秒来自候选阶段。该数据应作为哈希索引改进效果的首选估计；实验 1 中从冷缓存到热缓存的 34.93% 总耗时降幅夸大了独立代码改动的效果。

## 实验 2a：Parquet 解码扩展性微基准

在修改生产环境读取器之前，只读微基准使用了同一文件中的行组 `[0, 96)`：共 3,145,728 行，`batch_size=100000`，且仅读取 `id` 和 `candidate_codes`。每次运行均校验行数。实验使用热缓存，因此隔离测量的是 Parquet 解码和 Arrow 数据物化，而非物理磁盘读取。

在同一进程中交替配置的单读取器结果如下：

| 模式                | 平均耗时 |      吞吐量 | 平均 CPU 核数 |
| ------------------- | -------: | ----------: | ------------: |
| `use_threads=False` | 19.216 s | 163.7K 行/s |          1.00 |
| `use_threads=True`  | 15.981 s | 196.8K 行/s |          1.02 |

Arrow 的该参数使耗时降低 16.83%，但占主导的候选字段只是一个 Parquet 叶子列，因此 CPU 并行度没有得到明显提升。

随后，将连续且互不重叠的行组范围分配给独立读取器：

| 读取器工作线程数 |    耗时 |        吞吐量 | 平均 CPU 核数 | 解码加速比 |
| ---------------: | ------: | ------------: | ------------: | ---------: |
|                2 | 9.846 s |   319.5K 行/s |          1.84 |      1.95x |
|                4 | 4.975 s |   632.3K 行/s |          3.19 |      3.86x |
|                8 | 2.484 s | 1,266.4K 行/s |          7.24 |      7.74x |

第二张表仅代表解码性能的上限测试，而不是端到端结果。该实验没有执行哈希匹配、`take`、候选提取或有序结果更新，并且只校验了数据覆盖范围，而未校验候选内容。实验表明，独立的行组读取器可以利用多核；生产版本必须按照全局输入顺序合并更新，才能保留“最后一个源记录生效”的行为。

## 实验 2b：Arrow 多线程完整流程

提交：`d0b8766b4fcb92b261c28288b4729b4dc73aba01`

完成受控的哈希索引对比后，为该工具的 Parquet 读取器启用 PyArrow 有序多线程列解码。`candidate_codes` 压缩后约占 39.0 GiB，而 `id` 仅约占 0.35 GiB。优化后的运行仍占满一个逻辑 CPU，并且几乎没有物理磁盘 I/O，因此解码和转换工作成为下一处瓶颈。`use_threads=True` 时，`iter_batches` 仍保持批次顺序，所以重复 ID 的“最后一个源记录生效”行为不变。

实验结果：

| 指标             |    哈希索引 | 哈希索引 + Arrow 多线程 |           变化 |
| ---------------- | ----------: | ----------------------: | -------------: |
| 端到端耗时       |   464.519 s |               434.214 s |         -6.52% |
| 用户态 CPU 时间  |   344.301 s |               345.412 s |         +0.32% |
| 系统态 CPU 时间  |   120.231 s |                90.886 s |        -24.41% |
| 平均 CPU 使用率  |     100.00% |                 100.48% | +0.48 个百分点 |
| 候选有效吞吐量   | 120.7K 行/s |             135.3K 行/s |        +12.10% |
| 候选扫描估算耗时 |     355.0 s |                 316.7 s |        -10.79% |

完整统计与之前所有运行仍然一致。Arrow 多线程使端到端耗时减少 30.305 秒，性能提升至 1.070 倍；估算的候选阶段耗时减少 38.317 秒。该改动主要降低了系统和解码开销，平均仍只使用约一个逻辑 CPU。这项改动有效且风险较低，但并不是真正的多核实现。

## 最终对比与建议

应优先采用热缓存基线与最终版本之间的受控对比：

| 指标         | 热缓存原版 |    最终版本 |             变化 |
| ------------ | ---------: | ----------: | ---------------: |
| 端到端耗时   |  599.451 s |   434.214 s | -27.56% / 1.381x |
| 候选扫描耗时 |    479.1 s |     316.7 s |          -33.89% |
| 候选吞吐量   | 89.5K 行/s | 135.3K 行/s |          +51.26% |

建议保留两项经过测量的改动。可复用哈希索引是主要修复，贡献了受控端到端耗时节省的约 82%。Arrow 有序多线程解码在不改变观测到的汇总统计的前提下，进一步带来了幅度较小的改进。

不应宣称最终实现能够有效利用这台 32 核主机。下一步优化应单独实施：将连续且互不重叠的行组范围分配给 4 个独立的 Parquet 读取线程。工作线程不能并发更新共享的候选矩阵，其匹配结果必须按照原始输入顺序合并，以确保重复商品 ID 继续保持现有的“最后一个源记录生效”行为。包含 96 个行组的微基准表明，使用 4 个读取器时原始解码速度可提升至 3.86 倍；但完整实现还需要结果等价性测试、受控的在途内存、多文件覆盖，以及完整的端到端测量。

所有完整运行都使用了 `--rate_only`，仅生成日志文件。最终运行后磁盘可用空间为 112 GiB，无需清理生成的结果目录。

## 验证范围

- 37 个 SID 碰撞单元测试全部通过，其中包括重复商品 ID，以及最后一个源候选值向重复行广播的行为。
